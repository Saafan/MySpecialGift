## 4.3 — Revert and re-land analysis

**No revert or re-land can be identified directly** — there is no history to search. Three pieces of code, however, are *shaped like* re-lands: they contain explicit compatibility paths for a previous implementation, which is what a fix-forward after a design change looks like.

1. **`migrateLegacyArtboard`** (`apps/web/src/components/editor/editor-canvas.tsx:96-142`). Its comment at line 119 reads: *"Remap content from a legacy full-bleed page or small centred artboard."* This is a data-migration path for designs saved under **two** previous artboard models. The `.playwright-cli/fullbleed1.png` artifact (2026-06-21) confirms the "full-bleed" model was real and was being tested at the end of the project.

2. **The `print-guide` cleanup** (`editor-canvas.tsx:328-331`): *"Drop any legacy print-guide objects from older sessions."* A separate visual guide object was once added to the canvas and then removed from the product; this code deletes it from restored designs. `e2e/user-journey.spec.ts:892` still has a test named `"91 - Canvas renders with safe zone indicator"`, corroborating that a guide/safe-zone existed.

3. **The Brand tab removal.** `e2e/user-journey.spec.ts:331-334` is literally titled `"29 - Brand tab removed; pan tool available"` and asserts `await expect(page.locator('button[title="Brand"]')).toHaveCount(0)`. Combined with `TEST_REPORT.md:72` ("Brand colors persist to localStorage ✅ PASS — BUG-E08 fix verified"), this shows a Brand-colours feature was built, bug-fixed (BUG-E08), and then **removed entirely**, with the pan tool taking its slot. The test was rewritten to assert the removal rather than deleted — a deliberate anti-regression guard.

#### BUG-P01 — Every controlled input in the right panel reverted immediately (rated High) {#bug-p01}

**This is the most consequential bug in the project's history, and its fix is the most important defensive pattern in the codebase.**

| Field | Value |
|-------|-------|
| **Evidence class** | DOC + CODE (fix visible in current code) |
| **Category** | **State bug, React re-render bug, UI bug** |
| **Symptoms** | Dragging the opacity slider snapped it back. Typing in X, Y, W, H, Rotation, Stroke Width, or Rounding reverted the value on the next render. Colour *swatches* worked; the colour *hex field* was unreliable. Seven-plus controls affected (`TEST_REPORT.md:108-121`). |
| **Root cause — quoted verbatim from `TEST_REPORT.md:111`** | *"The `EditorRightPanel` component uses a `forceUpdate` state counter that is only incremented on specific Fabric.js canvas events (`object:modified`, `object:moving`, `object:scaling`, `object:rotating`). When the component's own `onChange` handlers call `activeObject.set(prop, val)` followed by `canvas.renderAll()`, none of these events fire. React's controlled component pattern then re-renders with the **stale** value from the unchanged `activeObject` reference (since `forceUpdate` wasn't triggered)."* |
| **The deeper mechanism** | Fabric mutates objects **in place**. React's reconciler sees the same object reference and the same `forceUpdate` counter, so it re-renders the input with the value it read at the top of the previous render — the pre-change value. Colour swatches were immune only because `<button>` has no controlled `value` prop. |
| **Resolution — three layers, all present in the current code** | 1. **Manually fire the event Fabric would not fire.** Every programmatic `.set()` is followed by `canvas.fire("object:modified", { target: activeObject })` — `editor-right-panel.tsx:435, 451, 469, 487, 513, 533, 289, 363, 827, 838`. This trips the `forceUpdate` subscriber at `:221`.<br>2. **Local shadow state for text inputs.** `NumberInput` (`:97-147`) holds its own string, with a `prevExternal` ref (`:113,117-120`) so canvas-driven changes overwrite it but the user's typing does not get clobbered. `OpacityControl` (`:49-53`) does the same for the slider.<br>3. **Debounced history.** `useDebouncedPushHistory` (`:83-94`) batches the resulting flood of `pushUndo` calls into one entry per 500 ms. |
| **Affected files** | `apps/web/src/components/editor/editor-right-panel.tsx` (all 953 lines are shaped by this fix); `apps/web/src/components/editor/print-area-panel.tsx:25-31` uses the same shadow-state pattern |
| **Hidden assumption revealed** | **That a mutable third-party object can serve as React's source of truth for a controlled input.** It cannot: React needs a value that changes identity or a re-render trigger, and Fabric provides neither. |
| **Race / timing** | Yes, indirectly. The debounce means a rapid sequence of edits collapses into one history entry, so undo granularity is time-based rather than action-based. |
| **Platform-specific** | No |
| **Regression risk** | 🔴 **The highest in the codebase.** The fix is **not structural** — it depends on every future `onChange` handler *remembering* to call `canvas.fire("object:modified", ...)`. There are currently 10 such call sites. Adding an 11th control and forgetting the line silently reintroduces the exact bug, in that control only, with no test to catch it. |
| **Regression test** | ❌ **None that can run.** `e2e/user-journey.spec.ts:399-410` (tests 37-38) sets a position value and an opacity value but **asserts nothing afterwards** — they are pure smoke tests. There is no unit test because `EditorRightPanel` cannot be rendered without a real Fabric canvas, and the web Jest suite cannot start at all. |
| **Lesson** | When you bridge an imperative, mutating library to React's declarative model, the bridge must be explicit and enforced — not a convention that each handler re-implements. |
| **Prevention** | (a) Wrap all Fabric mutation in a single `mutateObject(fn)` helper that performs the `.set()`, the `renderAll()`, the `fire()`, and the debounced push — so the pattern cannot be forgotten. (b) Add a component test per control asserting that typing a value and blurring leaves it in place. (c) Consider `useSyncExternalStore` with a Fabric-event subscription so React subscribes properly instead of polling via a counter. |

## What a future maintainer should take from this

1. **The URL-parameter pattern (Pattern 1) caused four bugs.** Before adding any page with query-string links, decide that the URL is the state.
2. **BUG-P01's fix is a convention, not a mechanism.** Wrapping Fabric mutation in one helper is the single highest-value refactor available, and it is also the one most likely to reintroduce the bug if done carelessly. Do it with tests in place first — which means fixing `apps/web/jest.config.ts:9` first.
3. **The 3D subsystem has 11 defensive comments and 0 tests.** It is the highest-churn code in the repo. Treat every constant in `product-3d.ts` and `product-print-limits.ts` as load-bearing until proven otherwise.
4. **Three of the nine "verified fixed" bugs in `QA_AUDIT_REPORT.md` have regression tests that would fail today** (BUG #1, #5, #6). The verification record is not trustworthy without re-running it — and it cannot be re-run until `playwright.config.ts:12` is corrected.
5. **There is no undo for this repository.** Before any refactor, create a git repository and make an initial commit. That is the cheapest risk reduction available and should precede everything else.
